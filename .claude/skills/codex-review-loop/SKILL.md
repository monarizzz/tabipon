# codex-review-loop

このリポジトリでは chatgpt-codex-connector[bot] が各PRに自動レビューコメント(P1/P2)を付ける。
人間(monarizzz)が対応し、`@codex` とメンションして再レビューを依頼する運用。
このスキルはその一巡の調査・対応・再依頼、および返信待ちの継続監視を行う。

レビューの観点とレビュー言語(日本語)は `AGENTS.md` の「コードレビュー」節が定義元。
codexの指摘を検証するときも、自分で追加の指摘を書くときも、そこに揃える。

## 全体の流れ

1. **調査**: `gh pr list --state open --limit 100` で全open PRを取得
   (`--limit` の既定は30。open PRが30件を超えると黙って切り捨てられるので必ず指定する)
   **`--author` で絞り込まない**。共同作業者やbot、fork由来のPRもcodexのレビュー対象であり、
   絞ると恒久的に見落とす
2. 各PRについて以下をすべて取得する。**コメント系APIは1ページ30件が既定のため `--paginate` を必ず付ける**:
   - `gh api --paginate repos/monarizzz/tabipon/pulls/<番号>/comments` … codexのインライン指摘
   - `gh api --paginate repos/monarizzz/tabipon/pulls/<番号>/reviews` … レビュー本体。
     codexが「指摘なし」や承認をレビュー本体だけで返すケースがあり、インラインコメント0件でも
     ここに最新の応答が入っている。返信済み/待機中の判別にはこちらが必要
   - `gh api --paginate repos/monarizzz/tabipon/issues/<番号>/comments` … 人間の対応コメント・`@codex`メンション有無
   - `gh pr view <番号> --json headRefOid,commits` … 指摘後にpushされたコミットの有無。
     人間がコメントを残さずpushで対応した場合、コメントだけ見ると未対応に誤分類してしまう
3. 状態を分類する。**指摘の日時と、その後のコミット日時・コメント日時を時系列で突き合わせる**こと:
   - **codexの応答自体が無い**(インラインコメント・レビュー本体のどちらにも
     chatgpt-codex-connector[bot] の投稿が1件も無い) → **レビュー未実施**。
     指摘なしと同じ「対象外」に入れてはいけない。新規PRなど、まだレビューが走っていない状態なので、
     `gh pr comment <番号> --body "@codex review"` でレビューを起動し、監視ループの対象に含める
   - 指摘なし(codexの応答は存在するが、その中に指摘が無い/承認) → 対象外
   - 指摘あり・未対応(指摘が現行コードでまだ解消されていない) → **修正対象**
   - 指摘あり・対応済みだが `@codex` 未送信 → **再レビュー依頼のみ**

   **「対応済み」は後続コミットの有無で判定しない。**指摘の後に別コンポーネントのコミットや
   ベースブランチのマージが入っているだけで対応済みに流れてしまい、未修正のまま
   `@codex` を送ることになる。指摘1件ごとに、指摘後の差分(`git log -p`/`gh pr diff`)か
   現行コードそのものを見て、その指摘が実際に解消されていることを全件確認すること。
   - `@codex` 送信済み・返信待ち → 監視継続
   - codexから承認/追加指摘の返信あり → 追加指摘なら再度2から、承認なら完了

## 調査はトークン節約のため下位モデルへ委任してよい

全PR分の `gh api` 呼び出しは件数が多くトークンを食うため、`Agent` ツールで
`model: haiku` のサブエージェントに調査(手順2-3の分類)だけを委任してよい。
ただし **分類結果は鵜呑みにしない**。標本だけの確認で済ませてよいのは
「対象外」「返信待ち(何もしない)」に分類されたPRだけで、
**コード変更・コミット・PRコメント投稿など外部に影響する操作を行う候補
(修正対象・再レビュー依頼対象)は、1件残らず自分で生データを確認する**こと。
確認するのは元の指摘コメント本文、最新コミット(`gh pr view --json headRefOid,commits`)、
指摘とコミット/コメントの時系列、**そして指摘該当箇所の現行コード**の4点。
時系列だけでは「無関係なコミットが入っただけ」と「指摘が実際に直っている」を区別できない。

特に間違えやすいのは、**codexの指摘が参照しているコミットハッシュが古いままのケース**。
指摘後にコミットを分割・リベースしていると、現行コードでは既に直っているのに
参照先が消えているせいで一見「未対応」に見える。現行コードを読めば判別できる。

## 修正対応

- PRのブランチ用worktreeは `AGENTS.md`「WorkTree」節に従って作る。
  `git worktree list` で既存のものを確認し、無ければ `git worktree add` で作る。
  **既存worktreeを再利用する場合は、編集を始める前に対象ブランチを検証する**こと:

  ```bash
  git -C <パス> branch --show-current   # 対象PRの headRefName と一致するか
  git -C <パス> status --short          # 未コミットの変更が無いか
  ```

  一致しなければ `git -C <パス> switch <headRefName>` で戻してから作業を始める。
  前回の並行作業でブランチが切り替わったまま残っていることがあり、
  そのまま委任すると別PRのコードを編集・検証してしまう。作業後の確認では手遅れになる。
  **このスキルの実行中に新規作成した worktree は、全PRの対応完了後に必ず削除する**
  (`AGENTS.md`「WorkTree」節)。放置すると巡回のたびに不要な作業ツリーが積み上がる。
  消すのは worktree だけでブランチは残す。元から存在した worktree は削除しない
- 検証コマンドは **`frontend/` で実行する**。リポジトリルートに `tsconfig.json` は無いため、
  ルートから `npx tsc --noEmit` を実行すると frontend が検査されないまま終了コード0になる:

  ```bash
  cd frontend && npm run typecheck && npm run lint && npm test
  ```

- `AGENTS.md` の規約(1コミット=1コンポーネント/1論点、各コミットの時点で型チェックが通ること、
  件名の prefix は8種のみ、何を・どこに・どうしたかを書く)に従う
- **`--no-verify` を使わない。**フックが落ちたら握り潰さずに原因を直す(`AGENTS.md`「基本ルール」)
- コード修正の実作業(ファイル編集・型チェック)は `sonnet` サブエージェントに委任してよいが、
  **git操作(commit/push)とPRコメント投稿は自分(呼び出し元)で行う**こと。
  理由: `git commit`/`push`/`worktree add` を含む指示文はAuto Mode分類器にブロックされることがある
  (特に `force-with-lease` 等の危険操作をサブエージェントへの指示に含めると高確率でブロックされる)。
  サブエージェントには「ファイル編集と型チェックのみ、gitは操作しない」と明記して依頼する
- 複数worktreeを並行操作する場合、サブエージェントが共有worktreeのブランチを
  勝手に切り替えることがある。作業後は `git status` / `git branch --show-current` で
  意図しないブランチ切り替えが起きていないか確認し、元に戻す
- 修正後は**コミットまでを既定とする**。`AGENTS.md`「基本ルール」のとおり、
  `git push` を実行してよいのは**ユーザーがpushを明示的に指示している場合のみ**。
  「codexのレビュー見て」のようにpushの明示が無い依頼では、コミットで停止し
  「pushしてよいか」をユーザーに確認する。当然 force push は行わない
- **未pushの修正がある間は** `@codex` メンションを送らない(リモートに修正が無く、
  再レビューしても意味がないため)。push許可が得られてから送る。
  ただしこの禁止は「pushすべき修正が手元にある場合」に限る。
  指摘が的外れ・既に対応済みでコード変更が発生しなかったPRは、
  そもそもpushする対象が無いので**例外**とし、説明コメント(下記)をそのまま送ってよい
- push 後は、PRに `@codex` から始まる日本語コメントで対応内容を簡潔に説明する
- 指摘が的外れ・誤解・(参照コミットハッシュが古いなどで)既に対応済みの場合は、
  コードは直さず理由を添えて日本語で説明コメントを返す。
  **この説明コメントも `@codex` から始める**こと。メンションが再レビューの起動条件なので、
  付け忘れるとcodexが説明を読み直さず、返信待ちの監視ループも始まらない
- UIに変更が出る修正をした場合は、PR本文の「## スクリーンショット」節を更新する
  (`AGENTS.md`「Issue・PRのスクリーンショット」節)

## 再レビュー依頼のみのPR

対応は既に完了しているが `@codex` メンションがまだのPRには、
`gh pr comment <番号> --body "@codex 対応済みです。再レビューをお願いします。"` を送るだけでよい。
件数が多い場合はループで一括送信してよい(1件ずつ `sleep 1` を挟む程度で十分)。

## 継続監視ループ

`@codex` を送った後、codexの再レビュー返信はすぐには来ない。
`ScheduleWakeup` で 900〜1500秒後に自分自身を再度呼び出すループを組む。
`prompt` には「全PRを対象に、直近の `@codex` メンションより後のcodexコメントが
無いか確認し、あれば妥当性検証→必要なら追加対応、無ければ待機継続」という主旨を書く。
このスキル(codex-review-loop)の存在を前提にしてよいので、詳細手順を毎回書き下す必要はなく
「codex-review-loop の要領で全PRの再レビュー返信を確認し対応せよ」で足りる。

全PRでcodexが承認 or 追加指摘なしになったら、ユーザーに完了報告して
`ScheduleWakeup(stop: true)` でループを終了する。
